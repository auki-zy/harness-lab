## 打开慢的主因

**三个接口串行 await**（600 + 650 + 550 ≈ 1800ms，而且第一个不返回后面根本不发）。改成 `Promise.all` 后降到 max ≈ 650ms。这是首屏慢的绝大部分。

## 切筛选卡的主因

按影响排序：

1. **派生状态反模式** — 筛选结果存 `useState` 再用 `useEffect` 回写，每次筛选白跑一整轮渲染（旧 → effect → 新）。改成渲染期 `useMemo`。
2. **`resize` 监听器写在渲染体里且从不摘除** — 每次渲染新挂一个，永久残留。这是"越用越卡"的元凶，也算内存泄漏。移进 `useEffect` + 清理 + rAF 节流。
3. **每行一次 `users.find`** — 480 × 60 ≈ 每次渲染 2.9 万次比较，换成 `Map` 索引。
4. **排序每次筛选都重做** — `orders` 只变一次，排序却是 O(n log n) 每键一次。提前排一次，利用筛选保序，memo 里只剩 O(n) filter。
5. **`Row` 三个 memo 打穿点** — 内联 `style` 对象、父级为每行生成的闭包、组件没包 `memo`。三个都修才生效。
6. **`key={i}`** 改 `key={o.id}`。
7. **输入框**用 `useDeferredValue`（需 React 18+），打字不再被表格重渲染拖住。

## 需要你知情的两点

- **行为变化**：原来三份数据是陆续落地的（指标卡、成员数、表格先后出现），现在同批出现。如果更想保留渐进渲染，正确做法是拆成三个独立 effect 各自 fetch——仍然并行，只是完成时间不同。
- **一个真实的功能 bug，我没动**：筛选用的是 `o.user`（`u-12`），但表格显示的是成员名（`成员 1`）。输入框写着"按成员筛选"，实际搜"成员"匹配不到任何东西。修它会改变筛选语义，超出性能范围，留给你定。
