# Dashboard 性能优化说明

日期：2026-09-15
文件：`src/Dashboard.tsx`

两个症状：**打开要好几秒**、**切筛选（以及输筛选词）卡**。下面按改动列，每条写清它针对的是哪个症状、为什么原来慢。

---

## 一、打开慢

### 1. 三个接口从串行改成并行（`useEffect` 里的 `Promise.all`）

**症状**：打开要好几秒。

原来是一个 await 接一个 await，`fetchOrders`(600ms) → `fetchMetrics`(650ms) → `fetchUsers`(550ms)，三份数据之间没有任何依赖关系，却排成了一队，首屏要等 **1800ms** 才开始渲染。改成 `Promise.all` 后总耗时取最慢的那个，约 **650ms**。

这是"打开慢"里最大的一块，也是改动最小的一块。

### 2. 成员查找从线性扫描改成 Map

**症状**：打开慢，且每次渲染都在重复付出这个代价。

原来渲染里有个 `userOf = (id) => users.find(...)`，在 480 行的 `map` 里每行调一次，每次都要扫最多 60 个成员 —— 单次渲染约 **2.9 万次比较**。改成 `useMemo` 预先建一个 `id -> name` 的 `Map`，查找降到 O(1)。

### 3. 行组件加 `memo`、把内联对象提到模块级、回调改稳定

**症状**：打开慢（以及后面切筛选卡）。

三个问题叠在一起，导致 480 行**每行每次渲染都全量重渲染**：

- `Row` 没有 `memo`，父组件一渲染 480 行全跟着渲染；
- `style={{ padding: 8 }}` 每次渲染都是新对象 —— 就算加了 `memo`，这个新引用也会让比较失败，等于没加。已提到模块级的 `ROW_STYLE` / `METRIC_STYLE`；
- `onPick={() => setQuery(o.user)}` 每行每次渲染都是新闭包，同样会打穿 `memo`。改成稳定签名的 `handlePick`（用 `useCallback`，把 `user` 作为入参传进去），行内再取 `order.user`。

### 4. 列表 `key` 从数组下标改成 `order.id`

**症状**：打开慢 + 切筛选时行内容可能错位。

原来是 `key={i}`。筛选一变化，数组长度和顺序都变了，React 按位复用 DOM 节点，导致本该复用的行被丢掉、不该复用的被留下 —— 既浪费渲染，也可能出现内容/点击行为对不上的情况。改成 `key={o.id}` 后，行身份稳定，React 能正确复用，对 memo 也才有意义。

---

## 二、切筛选卡

### 5. 筛选 + 排序从 `state + useEffect` 改成 `useMemo` 派生值

**症状**：切筛选卡。

原来筛选结果存在 `rows` 这个 state 里，靠 effect 去同步：`orders`/`query`/`status` 一变 → 先用**旧的** `rows` 渲染一次 → effect 跑过滤排序 → `setRows` → 再渲染一次。每次筛选手动多绕一圈渲染，而且 `rows` 和它的数据源之间是可失同步的冗余状态。

改成 `useMemo` 直接派生：一次渲染就算好，没有中间态、没有多余那一遍。

### 6. `toLowerCase()` 从循环里提到循环外

**症状**：输筛选词时卡。

`o.user.toLowerCase().includes(query.toLowerCase())` 里，`query.toLowerCase()` 在 480 次迭代里被重复算了 480 遍。提到 `useMemo` 外面算一次。

这个改动本身很小，但它和上面第 3 条叠加才是"输一个字就卡"的真正原因：每次按键 480 行全量重渲染 + 每行一次字符串分配。光有 `useMemo` 不够，光有 `memo` 也不够。

> 没有加输入防抖：过滤 480 条本身是微秒级的，加防抖只会让人感觉输入有延迟，属于把问题按错地方。真正贵的是重渲染，已经在第 3 条解决了。

---

## 三、顺带修掉的一个 bug（不是性能问题，但会放大卡顿）

### 7. `resize` 监听补上 `useEffect` + 清理

**症状**：窗口尺寸变化时异常卡；也是内存泄漏。

原来这行直接写在组件函数体里：

```tsx
window.addEventListener('resize', () => setWidth(window.innerWidth));
```

它在**每次渲染**时执行，而且**从来不解绑**。于是每渲染一次就多一个监听器，每个监听器都会 `setWidth` → 又触发渲染 → 又多挂一个监听器 —— 渲染次数随交互次数**滚雪球式增长**。这个增长会污染上面所有优化：用一会儿之后，切一次筛选触发的渲染量比刚打开时多得多。

已改成标准的 `useEffect(..., [])` + `removeEventListener` 清理。另外 `useState(window.innerWidth)` 改成惰性初始化 `useState(() => window.innerWidth)`，避免每次渲染都白读一次属性。

## 四、这次**没有**做的事

- **没加列表虚拟化**。480 行全渲染仍然偏重，虚拟滚动（`react-window` 之类）能再降一个量级，但会引入依赖、并且会改变 DOM 结构（影响外部 CSS 和测试）。当前量级下第 3 条的 `memo` 已经把主要开销去掉了，先不做。行数上到几千时值得回头做。
- **没做接口缓存/共享**。三个 `fetch*` 仍是各自组件挂载时取。如果看板会在多页间来回切，应该提到上层或用 SWR/React Query。
- **没加防抖**，理由见第 6 条。
