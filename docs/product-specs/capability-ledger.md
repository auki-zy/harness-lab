# 产品规格：能力台账页面

## 用户与目标

- 用户：仓库维护者本人（一人使用）。
- 目标：判断某个候选能力**值不值得继续用 / 采纳**，并能追到支撑这个判断的证据。

## 首页（台账列表）

- 顶部只保留：标题、一行说明、一行规模事实（已收录 / 已采纳 / 试用中）、一个「评测规范」链接。
  **不展示**原始数据入口：页面是唯一读数入口，JSON 不往外透出。
- 每个能力一行，行内依次是：
  1. **结论印章**（采纳 / 挂起 / 放弃 / 重试 / 未评估 / **可用 / 不可用**）——后两个是 MCP 可用性检查的结论：问的是"能不能用"，不是"值不值得装"（见 `evals/schema.md` 第九节）；
  2. 能力名称 + **一句话说明**（`description`：这个能力是干什么的——行内不写结论，结论由印章表达）；
  3. 标签 chips（`维度 | 取值` 两段式，维度名在浅底小格里，取值单独一段）；
  4. 右侧：这次是怎么试的（A/B 对照条，或"没有对照组"的说明）、试过几次与最近日期、**已采纳能力的安装命令 + 复制按钮**、「看完整记录」。
- 人评、模型、来源、路径都不在行上——它们属于详情。
- 行上那句说明**必须可溯源**：第三方能力是上游描述字段的直译、自研能力是自己规格文件的原文，来源写在详情的「说明来源」里；`src/shared/ledger.test.ts` 会拦住空说明与"把结论写进说明"的写法。

验收标准：不了解评测流程的人也能读懂每行的结论与理由（文案不得只出现 A / B 字母或裸数字）。

## 搜索

- 一个输入框，**只匹配名称与一句话说明**；来源、标签、试用内容不参与搜索（要按来源/标签找，用下面的筛选）。
- 无结果时给出下一步动作。

## 标签筛选

- 维度：**类型 / 用途 / 阶段 / 来源**（曾有的"风险面"维度已移除）。
- 每个取值显示命中数量；数量为 0 的取值不可点。
- 同一维度内多选 = 任一命中即可（OR）；不同维度之间 = 同时满足（AND）。
- **选中态 hover 必须仍然看得清**：选中项保持白字、只把底色压深。
- 待确认取值与正式取值同样可筛，用虚线边框与「待确认」标记区分。
- 提供"清空筛选"，并显示当前已选条件数量。

## 详情记录（两级抽屉）

抽屉标题只有能力名 / 试用标题，**不加 eyebrow**。模块固定五个，按顺序：

**一级（能力记录）**：

1. **结论**：**只有一个印章**（采纳 / 待确认 / 挂起 / 放弃 / 重试 / 未评估）——不再配口语结论、说明或元信息；"这是什么"在台账行上，"为什么"在下一个模块里。**印章只反映事实**：`采纳 / 已放弃` 只能来自人的结论（见模块 3），机器跑到证据够只给「待确认」。
2. **采纳原因 / 放弃原因**（试用中显示"判定依据"）：一句话结论（`summary`），说清为什么是这个结论。
3. **我的结论**：**采纳与否由人给**。
   - 汇总：`N 条试用人评：👍 x · 👎 y`＋`其中 k 次选了「加载能力」那版`（`humanSummary()`）、最近一条评价（👍/👎 · 选了哪版 · 理由 · 日期）；
   - 机器建议：`ready` → "机器判定达标（连续通过、无退步），采不采纳等你说一句"；其它结论也如实写；
   - 已经给过结论时显示结论本身（`你的结论：采纳 · 日期 · 理由`）；
   - 入口（**只在 dev**）：`采纳这个能力` / `不采纳` 两颗按钮 + 可选理由（≤300 字）+ **二次确认**（`Modal.confirm`，写明会写进 `capabilities.json` 的 `humanDecision` 并同步状态）。机器**不会**替你采纳，所以这是终局按钮。
4. **如何使用**：安装命令 + 复制按钮（字段来自登记的 `howToUse`）；没记录时给一句说明。
5. **试用记录（N 次）**：一张**紧凑小表格**（AntD `Table size="small"`，**一页 5 条、分页**），列是「**结论**（印章，96px：放得下三字结论如「待确认」）· **日期**（只留 `月-日`，年份没信息量）· **任务**（定宽 150px + 省略号，完整值在 hover 的 title 里——任务 id 是给人核对的，不是给人读的）· **方式**（两个字：对比 / 模拟 / 实跑 / 探针，全称与解释在 title 里）· **人评**（只有一个记号 👍 / 👎 / —，完整说法"赞 · 选了 B"在 title 里）· **详情**」，最近一次在最前面。一级里**不展开**任何单次细节。
6. **来源与标签**：来源仓库与许可一行 + **说明来源一行**（`descriptionSource`）+ 标签 chips；有待确认标签时给出提示；末尾一行只写本地位置。

**二级（试用详情，点「看详情」打开）**：这一次试用的完整过程——**只讲这一次，不引用别的试用的结论或证据**。结构分三层，**重点是第一层**：

> MCP 的探针记录在标题旁标「**可用性检查**」（不是"试用"）：它只说明这个 server 能用，明细里会给一行**功能清单（tools/list）**；这类记录永远拿不到"已采纳"（见 `evals/schema.md` 第九节）。

1. **前后对照（主角，紧跟结论）**：一块两栏对照板——A（不加载能力）与 B（加载了能力）各一栏，每栏依次是
   - 条件名 + 它代表什么（`A：不加载这个能力` 只显示后半句，避免和左上角的条件名重复）；
   - **结果**：`✓ 做到了` / `✗ 没做到` / `— 没有记录结果`，带语气色（玉色 / 朱色）；人评选中的那栏加"人评选了这版"标记 + 高亮边框；
   - **两三个关键数字**：按优先级取「产物文件大小 → 总 token → 耗时 → 工具调用次数 → 输出 token」，带单位；
   - **产物**：「打开产物」按钮 + 文件名（拿不到产物时写明"没有可打开的产物"）。
   板子下面一句**对照结论**：`两版都做到了任务要求；产物 0.6 KB → 0.7 KB（变大 17%）；token 80,731 → 83,451（变多 3%）；耗时 85.4 秒 → 85.5 秒（基本持平）`——**只讲 A → B 的事实，不判"哪个更好"**（"哪个更好"由后面的「系统小结」单独给，见下）；单条件或没有可比数字时不显示这一行。
   板子底下再挂一颗「**对比两版**」（两侧都有产物时才出现）：并排 diff——左 A / 右 B，新增行绿色、删除行红色、行号各归一侧，顶上一句 `B 比 A 多 5 行：新增 12 行 / 删除 7 行`。**代码 / 组件类技能最该看的就是"改了哪几行"**（以前只能各自「打开产物」并排开两个标签页人肉比）。超过 1200 行不算逐行差异、只给结论 + 指回「打开产物」；读不到产物时给一句人话，不白屏。
2. **细节（想看再看）**，按顺序：
   - **客观指标（全部维度）**：标题右边有个 **`?`**（hover 出 tooltip，`measureRules()`）：**每个维度怎么读的规则集中放在那里**——"token 越少越省""缓存命中越多说明上下文复用越好""交互轮次/工具调用越少越利落""只有'是否做到任务要求'参与判定""差 5% 以内算持平"。表格里的"差别"列**只说事实**（`B 比 A 多 3%`），不再每行重复一句"越少越省"（同一句话说十几遍，表格反而更难扫）。列名按本次实际条件生成，拿不到的维度不摆空行，数字带单位（`80,731` 是 token、`85.4 秒`、`8 次`）；
   - **系统小结：哪一版更好**（客观指标之后紧接着给）：
     - 先分两栏说 **A / B 各自好在哪、差在哪**（每侧最多 3 条"好："、2 条"差："，被推荐的那栏标出来；没有任何可比证据时写"没有可比的证据"）；
     - 再给**一句推荐**，按写死的规则：一版做到另一版没做到 → 推荐做到的那版；两版都做到 → 人评优先，没人评就比 总 token → 耗时 → 工具调用 → 产物大小（差 5% 以内算持平）；各有胜负就如实说各有胜负；**两版都没做到 → 不给推荐**（先改任务说明或判据）；
     - 最后一行把**依据**（规则速记）原样写出来，并说明"这里只判这次对照哪一版更好，值不值得采纳另由客观通过率决定"——免得看起来像凭空冒出来的意见；
     - 这个模块**只判这一次对照**：不改判定、不改能力状态（规则与边界见 `evals/schema.md` 第六节「系统小结」）；单条件试用或两侧都没有可比数字时整个模块不出现；
   - **评审人怎么说** + 人评入口（👍/👎 + 可选理由 + 二次确认，见下节）；
   - **这次是怎么跑的**：任务说明、试用方式（受控对比 / 模拟场景 / 真实项目使用，带一句说明）、评判方与模型；离线自检的提醒也在这里。标题与其他模块**完全一致**（同一个 `sheet__title`；曾经单独压暗一档，反而显得像另一种层级，已去掉）；
   - **为什么这么判**（含置信度解释）；
   - **对比证据链**：**只有可复现的评判才展示**——`judge` 含 `llm` / `auto` 时给一个**左右分栏的查看器**（见下）；只由人评的试用**不展示证据模块**，改成一句按试用方式给准确说法的说明（受控对比 → 产物在「条件」里；模拟场景 → 产物在仓库里；真实项目使用 → 项目在别处，只留结论）。
3. 页脚一行：任务 id。

**证据链查看器**（一次跑动辄十几二十个文件）：这一节**只回答一个问题——这次凭什么判成这样**。顶上一句「怎么证明的」，下面就是判定结果；原始文件收成一行折叠入口（A/B 各自的产物在详情顶部的对照板里已经能直接打开，这里不再重复摆一遍）。

- **怎么判的**（默认显示，撑死几行）：从判定记录（`result.json`）读出来的
  - 一行一个用例：`用例 id ｜ A 2/3 ✓ ｜ B 3/3 ✗`（得分 + 通过与否，颜色分玉色/朱色）；
  - 一行一条判据：左边判据名（过长截断，hover 看全），右边两列是 A / B 的 ✅ / ❌；
  - **只解释没过的**：下面用一两句列出"哪一侧没过、为什么"（判定依据原文）——**全过的不用摆理由**，这是上一版"表格里塞折叠长文"最乱的地方；
  - 读不出来（没有 `result.json` / 结构认不出）就说清楚，指向原始文件，不硬编。
- **原始记录（N 个文件）**：一行折叠入口，展开才是"左边分组文件列表 + 右边原文"的查看器（分组与文件类型说明见下）。**技能自带那组默认折叠**。
- 原始文件视图的分组：A 版产物 / B 版产物 / 判定记录（工具报告）/ 随技能一起进去的文件 / 其它，每行标"这是个什么文件"（逐条用例结果、对照摘要、完整报告、实现代码…）。
- 切文件时**内容区不塌**（代码块 ≥240px、内容区 ≥300px，加载中沿用同一个盒子并压暗）——不然"读取中"（一行）与代码块（十几行）来回替换，看着就是一闪一闪的。
- **必要性**：证据链留着（"结论可复核"是这个仓库的立身之本），但**只留能被追问用到的那一层**：先说清怎么证明的，再给逐条判据，原文按需展开。

> 验收：打开一条试用，**第一屏就能看到"两版各自做到没有、产物在哪、差在哪"**；任务说明、评判方、模型、证据清单这些都属于"想知道细节再看"，不许插在对照前面。

## 发起评测（页面）

页眉上的「发起评测」按钮打开一个弹窗（**只在 dev 提供**：静态构建里没有 `/api/eval/*` 接口，按钮自动隐藏，页面退回纯展示）。弹窗就是一个 **AntD Form**：两格输入 + 页脚两颗按钮，没有别的可选项。

| 位置 | 是什么 | 行为 |
|---|---|---|
| 表单第 1 格 | **能力**（`Input`，label「能力」+ 右侧「技能市场」入口） | 名字对上候选/已采纳 → 直接跑它的评测配置；像 `owner/repo` 或链接 → 拉取 + 自动设计针对性用例 |
| （展开后）**技能市场** | 按**名称 / 描述关键词**搜 [skillsmp.com](https://skillsmp.com/zh/search)，结果显示「技能名 · ★ 星数 · 描述 · 作者 + 来源」 | **点结果 = 填进「能力」**（市场给的是 `github.com/o/r/tree/main/<技能目录>`，正是我们认的来源写法）；点行尾的「评测」= 填好并**直接开跑**。搜不到（或市场不通）时说一句人话，手工填照旧能用 |

> 市场搜索走**服务端代理**（`GET /api/eval/market?q=…&limit=…` → `skillsmp.com/api/v1/skills/search`）：避开跨域，也方便把"至少两个字""市场返回 502"这类情况写成一句人话。它是**找候选的便利入口**，不是依赖——市场抽风不影响手填 `owner/repo` 或链接。

| 表单第 2 格 | **提示词**（`Input.TextArea`，4 行高、上限 4000 字、带字数） | **可选**：填了就按它跑 A/B——**A 只给这段提示词 / B 再附上技能正文**，由 LLM 裁判（`agent_judge`，`judge.model` 走内部网关）判达标；不填就用该能力已有的用例。label **右对齐**一个**「根据能力生成」**：填的是**已在册的名字** → 直接读它的 `SKILL.md`；填的是**来源链接**（比如刚从技能市场选的那条）→ **先把它拉进候选池再读**（并把"已拉取"写进日志），起草一条贴合它的任务（**交付物形态跟着能力走**：视觉类给页面、代码类给小程序、流程类给文档），只填进输入框、**不自动开跑**——你改完再点「提交」 |
| 页脚右下角 | **关闭** + **提交**（Primary） | 「提交」在「关闭」右边，就是原来的「开始评测」。**提交成功后弹窗自己关掉**（评测是后台任务，见下一节） |

**表单下方不挂常驻提示**：能跑的时候一句话都不说（反馈全部来自按钮状态与运行日志）。只有"点了也跑不了"时才给一条 **Alert** 说明原因，并把「提交」置灰：

| 为什么跑不了 | 弹出来的话 |
|---|---|
| 类型没开放（子代理 / MCP） | 「… 的评测入口暂未开放（先只开放技能）」+ 一句"能力本身可以在台账里看" |
| 没有可用引擎 | 「技能评测需要一个能用的引擎（内部网关已内置）」+ 缺什么 + `claude auth login` / `codex login` 具体命令 |
| 名字对不上、也不像链接 | 「没找到「…」，也不像 owner/repo 链接」 |

**没有任何可选项**——这是被"按钮文字太多、用不来"和"用途标签/报告路径看不懂"两轮反馈逼出来的：

| 曾经要人选的东西 | 现在怎么定 |
|---|---|
| 三段工具（技能 / 子代理 / MCP） | 按能力类型自动定：技能→skill-up、子代理→promptfoo、MCP→协议探针 |
| 引擎（claude / codex / …） | **内置**：`claude_code` 走内部网关（Athen），模型默认 `deepseek-v4-flash`，`ATHEN_MODEL` 可换 |
| 用途标签 | 自动设计用例时一并判定（只能从 `evals/tags.json` 已登记的取值里挑），写进能力登记，事后可手改 |
| 「已有报告路径」（导入） | **从界面去掉**（概念太绕）；CLI 仍保留 `…-bridge.mjs import` |
| 官方 Inspector 交叉验证 | 从界面去掉（CLI 的 `node tools/mcp-probe.mjs --inspector` 仍在） |

**按类型各自会发生什么**（**子代理 / MCP 的入口与筛选先注释掉了**，见 `src/shared/entries.ts`）：

| 类型 | 输入候选名 | 输入链接 | 成本与结论 | 入口 |
|---|---|---|---|---|
| 技能 | 跑它 `evals/` 里已有的用例 | 拉取 → 按 `SKILL.md` 自动出题 → 校验 → 跑 | 一次 A/B 的模型花费；结论 采纳 / 挂起 / 放弃 / 重试 | **开放** |
| 子代理 | promptfoo 跑 A（无规格）/ B（带 `AGENT.md`），走内部网关真模型 | 不支持 | 一次 A/B 的模型花费；同上 | 注释掉（提示"暂未开放"，按钮不可点） |
| MCP | 协议探针：握手 / 功能清单 / 样例调用 | 不支持 | **零成本、秒级**；结论只有 **可用 / 不可用** | 注释掉（同上） |

> 类型筛选同样受这个开关约束：`类型` 维度只列已开放的类型（现在只有「技能」），不出现「子代理」「MCP 服务」两个筛选项。
> 服务端也拦着（`/api/eval/run` 会以「…的评测入口暂未开放」拒绝未开放的工具），所以不是"只藏了按钮"。

**行为**由输入内容决定，不需要人选：

- 输入能对上候选/已采纳里的**名字** → 直接用它的评测配置跑（`POST /api/eval/run`）；
- 输入像 `owner/repo` 或链接 → 走 `POST /api/eval/auto`：拉取进候选池 → 按 `SKILL.md` **自动设计针对性用例**（见 `evals/schema.md` 3.4）→ `skill-up validate` → 跑 → 落账；
- 名字对不上、也不像链接 → 弹一条"没找到「…」，也不像 owner/repo 链接"，「提交」不可点。

自填提示词的用例落成 `evals/cases/ask-<id>.yaml`，配置单独放 `evals/eval.ask.yaml`（**不动技能原有的用例套件**），结果照常进台账（`task.id` = `ask-<id>`）。

## 正在评测（后台任务）

发起评测是**后台任务**：一次评测要跑十几分钟，**提交成功弹窗立刻关闭**（不再把人关在一个只能等的窗口里），这次运行挂到首页列表顶上的「正在评测」区块，随时点开看进度。

| 在哪 | 长什么样 | 行为 |
|---|---|---|
| 首页「正在评测」区块 | 一行一次运行：**能力名 · 状态印章 · 发起方式 · 跑了多久 · 日志最后一行 · 「看进度」**；区块标题带「N 个在跑」 | 有任务才出现（没有就不占地方）；跑着的行底色是浅蓝（和「评测中」印章同一个蓝），跑完变玉色「完成」/ 红色「失败」 |
| 点「看进度」 | 弹出一个进度窗口：抬头 `评测进度 · <能力名>`，下面一行状态 + 已跑多久，再下面是**完整日志**（自动贴底） | 跑着的时候每 1.2 秒自己刷新；窗口里那颗「关闭」只关窗口，任务照跑 |

**怎么拿到这些状态**：服务端把每次运行登记在内存里（`{id, 能力名, 工具, 发起方式, 开始时间, 结束时间}`），页面每 **2 秒**问一次 `GET /api/eval/runs`（没有在跑就降到 8 秒），所以**关掉弹窗、刷新页面都不影响**——从哪个入口发起的都看得见（弹窗、技能市场的「评测」，甚至命令行里跑的，只要是同一个 dev server）。日志正文不跟着列表走（列表只要一行进度），点开才取 `GET /api/eval/run?id=`。

**跑完的瞬间自动重读台账**：任务从"跑着"变成"跑完"时页面会 `refreshAppData()`，新的试用记录与新的机器结论直接出现在下面的列表里——不用手点「刷新台账」（那颗按钮已经撤掉）。

> 三个细节都是踩出来的：① 状态里带**日志最后一行**（"跑到哪了"比"跑了多久"更能说明问题）；② 列表**只收最近 2 小时**的运行（更早的没必要挂在首页）；③ 服务端返回的形状页面**不许直接信**（拿到非预期结构就当"没有在跑"）——jsdom 里用一个通用 fetch 替身时，整页曾因为 `runs` 是 `undefined` 直接崩掉。
>
> **时间一律用服务端的值**（第四个坑，2026-09-14）：进度窗口显示"已跑 X"必须取 `run.startedAt` / `run.durationMs`，**不许在本地拿"窗口是什么时候打开的"当起点**——踩过：弹窗里自己 `Date.now()` 计时，刚打开永远显示"已跑 0 秒"，而任务其实已经跑了 6 分钟。服务端每次回报都重算（跑着的 = 到现在、跑完的 = 定稿时长），所以这个数字跟着 1.2 秒的刷新自己会走；`GET /api/eval/run?id=` 因此也把 `run` 一并返回，`RunProgress` 拿到就用，列表那一行与本窗口显示的是同一个来源。

**唯一的硬前提**：技能评测需要一个能用的引擎（装了 ≠ 能用）。没有可用引擎时：弹出上面那条 Alert 说明缺什么、给出 `claude auth login` / `codex login` 的具体命令、置灰「提交」——而不是让你跑出一个没信息量的「重试」。

**判定规则**（写死在 `tools/lib/trial-record.mjs` 的 `decide()`，页面不提供"下结论"的按钮）：报告里没有 B 侧结果或 B 侧全是工具报错 → `retry`；B 没全过 → `reject`；B 全过且此前已有 ≥1 次可复核试用通过 → `adopt`；否则 `hold`。人评只作附加信号——**再点一次「提交」就是第二次试用**。

**接口边界**（`vite.config.ts` 的 `evalApiPlugin`）：`POST /api/eval/auto` 只接受 `NAME_RE`（能力名）或 `SOURCE_RE`（`owner/repo` / URL），并**拒绝**任何 `engine` 参数（引擎内置，客户端不能指定）；`/api/eval/run` 的工具白名单是 `skill-up` / `promptfoo` / `mcp-probe`；参数由服务端按工具拼，**客户端不能传任意命令**。两个 POST 都**立刻返回** `{ runId, run }`（`run` 就是列表要的那一行：能力名 / 工具 / 发起方式 / 状态 / 已跑多久 / 日志最后一行），子进程输出写 `.trial-runs/<id>.log`；进度由 `GET /api/eval/runs`（列表，2 秒/8 秒轮询）与 `GET /api/eval/run?id=`（单次完整日志）提供。

## 人评入口（页面）

试用详情（二级抽屉）的「评审人怎么说」模块里，**人评下面就是写入口**（同样只在 dev 出现，静态构建退回只读并说明原因）：

1. **选 👍 赞 / 👎 踩**：两颗 toggle 按钮，`aria-pressed` 表达当前选择；**没选之前不许有任何一颗看起来已选中**（踩过：AntD Segmented 在 `value=undefined` 时会自己把第一项渲染成选中，看起来像已经选了 👍）；
2. **理由输入框**：可留空，最多 300 字，带字数提示；输入时旁边实时显示"将记录：👍 赞，理由「…」"或"…，不写理由"——提交前就把要写什么说清楚；
3. **「提交人评」**：必须选过 👍/👎 才可点；点它只弹**确认框**（`Modal.confirm`，写明会写进 `evals/trials/<id>.json` 的 `humanReview` 并重新聚合、且人评不改变判定），点确认才真的写；已经有人评时按钮文案变成「更新人评」，结论与理由都没改动时保持禁用，避免重复提交。

> **写完数据就地刷新，不整页重载**（2026-09-11 改）：提交人评 / 给能力下结论之后，页面调 `refreshAppData()`（dev 的 `GET /api/eval/data`）重读聚合产物并通知订阅者，**抽屉、二级试用、滚动位置全都留着**——以前是 `window.location.reload()`，一次确认就把正在看的东西全冲掉了（用户反馈）。数据源是个极小的订阅式 store（`src/shared/data.ts` 的 `useAppData()`），页面从此不吃"打包时那份快照"。

验收：不选就提交 = 不可能；点一下就写库 = 不可能（必须过确认）；写进去的永远只是这个人自己给的（见 `evals/schema.md` 第五节的保留规则）。

## 非目标

- 不做在线编辑：数据只从 `evals/` 生成，页面只读。**唯一例外是人评入口**（`POST /api/review`，只写 `humanReview` + `judge` 两个字段，且只在 dev 提供）——因为人评本来就是"人的判断"，只能在界面上产生。
- 不做多用户、权限、登录。
- 不做实时刷新：改数据后重新跑 `npm run data`。
- 不暴露原始 JSON（既无按钮，也无 `/evidence` 路由）。
